#### Context

Accessibility is LOCKED DECISION 10 (CLAUDE.md §2): **WCAG 2.2 AA on every platform** (iPadOS, Android, Web), platform screen readers for all chrome, and OCR-backed alt-text for handwriting. It is a **build gate, not a phase** — `docs/design/accessibility.md` states a surface is not done until it passes the criteria there. The hard part is that the ink canvas is a bitmap/vector surface that is **opaque to assistive technology**, so we must build a **parallel accessible model** on top of the canvas on every platform (`accessibility.md` §3; PRD-CO-330). This is also a market wedge: no ink app exposes handwriting to screen readers well (`prd-04` §8, user-pain idea #20), and Sane can because it OCRs on-device. This epic delivers semantics for all chrome, the parallel canvas tree, Dynamic Type, reduce-motion, OS display-setting adaptation, keyboard/switch/voice operability, non-gesture alternatives, colour-blind and motor-assist inclusive features, captions, automated a11y tests, and the pre-beta audit + Apple Accessibility Nutrition Labels. Grounding: `docs/design/accessibility.md` (primary), `docs/product/prd-04-sharing-collaboration-ai-study-a11y-i18n.md` §8 (PRD-CO-310–339), `docs/design/gestures-and-shortcuts.md` (non-gesture alternatives), `docs/design/design-system.md` + `docs/design/tokens.json` (contrast/tokens), `docs/design/screens-and-flows.md` (per-screen mapping).

**Expose Semantics for all app chrome (name, role, state, value)**

| Security controls | `MASVS-PLATFORM-1`, `MASVS-PRIVACY-3`, `CWE-532` |
| Extra labels | agent-ready |

#### Context

WCAG 2.2 SC 4.1.2 (Name, Role, Value) requires that **every custom-drawn control exposes name/role/state/value** to the platform a11y API (`accessibility.md` §2, PRD-CO-321). Sane's chrome is built from custom `sane_ui` widgets (palette dock, page rail, chips, segmented controls, toggles, share roles), not native controls, so nothing is accessible unless we attach `Semantics` explicitly. This issue establishes the semantics conventions and applies them to the shell and editor chrome that ship in M1, with the same conventions reused as Library, Templates, Share, Search and Settings chrome land in later milestones (per-screen requirements in `accessibility.md` §10). Without it, VoiceOver/TalkBack/NVDA read blank or wrong labels and the app fails the store nutrition labels.

#### Scope

**In:** a documented semantics convention (label/role/state/value/hint patterns) baked into `sane_ui` components — buttons, icon buttons, chips, segmented controls, toggles, sliders, list rows, tabs, nav items; the editor toolbar (Undo announces disabled when the stack is empty; Bookmark filled/empty), the tool palette (each tool a button with selected state; colour dots labelled by **name**; width dots labelled S/M/L), the page rail (thumbnails as a list, item 'page 3 of 12, bookmarked'); `MergeSemantics` for icon+label clusters, `ExcludeSemantics`/`BlockSemantics` for decorative art; `SemanticsService.announce` for toasts mirrored to a live region (`accessibility.md` §3.3).

**Out:** the parallel **canvas object** tree ([SN-A11Y-003](a11y.md#sn-a11y-003)) and OCR descriptions ([SN-A11Y-004](a11y.md#sn-a11y-004)); keyboard focus order ([SN-A11Y-008](a11y.md#sn-a11y-008)); the automated semantics tests ([SN-A11Y-016](a11y.md#sn-a11y-016)) — this issue's own widget tests assert labels, the suite generalises them.

#### Acceptance criteria

- [ ] Every interactive `sane_ui` component exposes a non-empty accessible name, correct role (button/checkbox/radio/slider/tab), and state (selected/disabled/checked/expanded) and value where applicable.
- [ ] Toolbar Undo/Redo announce their disabled state when the op-log stack is empty; Bookmark toggle announces filled/empty; Pro-gated actions announce 'Pro'.
- [ ] Colour swatches announce the colour **name** (not hex) plus selected state; width dots announce S/M/L; the visual uppercase of `label`-role text never leaks into the accessible name (original casing).
- [ ] Decorative art (login art panel, avatar colour, marketing pills) is excluded from AT via `ExcludeSemantics`.
- [ ] Toasts are announced politely via `SemanticsService.announce` and are non-interruptive.
- [ ] Verified with VoiceOver, TalkBack and NVDA that each M1 chrome control reads correctly.

#### Technical notes

Use Flutter `Semantics` widgets and the `SemanticsProperties` fields (`button`, `selected`, `enabled`, `toggled`, `slider`, `value`, `hint`); reuse them inside `sane_ui` so screens do not re-wire semantics per instance. Colour names come from the ink palette naming table (feeds [SN-A11Y-011](a11y.md#sn-a11y-011)). Announcements map to the design's toasts (`screens-and-flows.md` §16). Follows ADR-0003; components from `docs/design/component-inventory.md` §9 (states every component must handle). Do not use the deprecated web canvas hit-regions.

#### Security & privacy

Accessible names for note-bearing chrome (a notebook title, a search snippet) are **user content** and MUST NOT be logged (CWE-532, MASVS-PRIVACY-3). Correct semantics is a platform-integration control (MASVS-PLATFORM-1). No egress; no secrets.

#### UX notes

Covers the Editor chrome (`accessibility.md` §10 'the hard screen') plus the shell; every look x dark mode must keep the same semantics (semantics are look-independent, but focus rings must stay >= 3:1 — see SN-DS-006). Targets: tool buttons 44, chrome 42, chips 34 — verify chips meet the platform floor with spacing (§2 SC 2.5.8).

#### Test plan

Widget/semantics: `app/test/a11y/chrome_semantics_test.dart` and `packages/sane_ui/test/a11y/component_semantics_test.dart` using `SemanticsTester`/`matchesSemantics` to assert name/role/state per component and editor control; a test asserts uppercase `label` roles expose original casing. Manual: VoiceOver/TalkBack/NVDA smoke on the editor.

#### Dependencies

SN-DS-003 (core components), SN-ED-002 (editor canvas + toolbar).

### SN-A11Y-003

**Build the parallel accessible canvas tree for note objects**

| Field | Value |
|---|---|
| GitHub | not published yet |
| Type | feature |
| Priority | p1 |
| Milestone | M2 Library & Documents |
| Platforms | all |
| Areas | a11y, editor |
| Size | L |
| SDLC | implementation |
| Parent | [SN-A11Y-001](a11y.md#sn-a11y-001) |
| Depends on | [SN-ED-002](editor.md#sn-ed-002), [SN-CORE-002](storage.md#sn-core-002) |
| Security controls | `MASVS-PLATFORM-1`, `MASVS-PRIVACY-2`, `MASVS-PRIVACY-3`, `CWE-532` |
| Extra labels | agent-ready, innovation |

#### Context

The ink canvas is opaque to assistive technology, so each drawn object must become an addressable a11y node in a **parallel tree** kept in sync with the document model (`accessibility.md` §3, PRD-CO-330). Flutter `CustomPaint.semanticsBuilder` emits a `CustomPainterSemantics` per object (rect + label + actions) and is the single implementation projecting to iOS `UIAccessibilityElement`, Android `ExploreByTouchHelper` and web ARIA. This issue builds the tree infrastructure over the object model (strokes/stroke-groups, shapes, images, text blocks, audio anchors, comments) once shapes/images/text exist in M2; decorative ink is excluded, and transient events are announced. It is the backbone that makes handwriting navigable by screen reader — a differentiator no ink competitor delivers.

#### Scope

**In:** a `semanticsBuilder` over the editor `CustomPaint` that produces one `CustomPainterSemantics` per note object with its rect (`accessibilityFrameInContainerSpace` equivalent), a label, a role/traits, and a custom-action set stub; grouping strokes into semantic **stroke groups**; `ExcludeSemantics`/null for decorative strokes (doodles, dividers) flagged in the model; `SemanticsService.announce` for transient events ('Saved', 'Deleted N strokes', 'Page 3 of 12', 'Link copied'); keeping the tree in sync incrementally as objects are added/moved/deleted without rebuilding the whole tree each frame; a page-level node exposing 'title, page X of Y'.

**Out:** the OCR transcript **content** of a handwriting block and object-type navigation ([SN-A11Y-004](a11y.md#sn-a11y-004)); audio-anchor play action and captions ([SN-A11Y-015](a11y.md#sn-a11y-015)); keyboard object navigation/nudge ([SN-A11Y-008](a11y.md#sn-a11y-008), [SN-A11Y-009](a11y.md#sn-a11y-009)); native-only rotor plumbing if Flutter's projection proves insufficient (spike inside [SN-A11Y-004](a11y.md#sn-a11y-004)).

#### Acceptance criteria

- [ ] Each non-decorative object exposes a focusable a11y node with a correct rect that tracks pan/zoom; decorative strokes are absent from the tree.
- [ ] A shape announces its recognised name + colour name ('green rectangle'); an image announces its alt text (never 'image'); a text block announces its text.
- [ ] The page node announces 'title, page X of Y'; navigating objects with a screen reader visits them in a stable reading order (top-to-bottom, left-to-right).
- [ ] Adding/moving/deleting an object updates the tree within one frame and posts the correct change announcement; no per-frame full rebuild on the hot draw path (CLAUDE.md §8).
- [ ] VoiceOver and TalkBack can focus each object; the web parallel semantics is present and tested explicitly (Flutter web is the weakest surface, §3.1).

#### Technical notes

Implement in `app/lib/editor/a11y/canvas_semantics.dart` feeding the editor `CustomPaint.semanticsBuilder`; read the object list from the `sane_core` document model (SN-CORE-002) and the decorative flag from the object metadata. Do not hop isolates on `PointerMoveEvent`; build/patch the tree on commit/idle, not during an active stroke (CLAUDE.md §8). Decorative exclusion and transient announcements per `accessibility.md` §3.2/§3.3. Custom actions are declared here as an empty extensible set that [SN-A11Y-004](a11y.md#sn-a11y-004) fills.

#### Security & privacy

Object labels are **user content** surfaced to AT on-device only; never log them (CWE-532, MASVS-PRIVACY-3) and never send them off-device to be generated (MASVS-PRIVACY-2, MASVS-NETWORK-1). On web the parallel semantics DOM is local to the viewer's device (no persistence, no egress). Correct projection is a platform control (MASVS-PLATFORM-1).

#### UX notes

Mirrors `accessibility.md` §3.2 ('what each object announces'); the whole page carries an `aria-describedby`/`accessibilityValue` transcript summary. Works across every look/dark mode (semantics are look-independent). Reduce-motion still applies to any focus-scroll animation ([SN-A11Y-006](a11y.md#sn-a11y-006)).

#### Test plan

Widget/semantics: `app/test/a11y/canvas_semantics_test.dart` builds a page of mixed objects and asserts node count, rects, labels, decorative exclusion, and change announcements on add/move/delete; a web-semantics test (`flutter test --platform chrome`) asserts the tree renders on web. Manual: VoiceOver + TalkBack object navigation on a real page.

#### Dependencies

SN-ED-002 (editor canvas/CustomPaint), SN-CORE-002 (object model).

| Field | Value |

| Milestone | M3 Audio & Recognition |

| Security controls | `MASVS-PRIVACY-2`, `MASVS-NETWORK-1`, `MASVS-PLATFORM-1`, `CWE-532` |
| Extra labels | agent-ready, innovation |

#### Context

WCAG 1.1.1 requires a text alternative for non-text content. A handwriting block's alternative is its **OCR transcript** ('Standing wave: two waves, same frequency...') used as the a11y label, with a `convert-to-text` custom action so a screen-reader user can act on it (`accessibility.md` §3.2, PRD-CO-310/PRD-CO-330). This is the market wedge — an ink app that reads handwriting aloud — and it depends on the on-device recognition pipeline (SN-HWR-001, ML Kit Digital Ink primary, Vision OCR fallback on iOS). This issue fills the object nodes created by [SN-A11Y-003](a11y.md#sn-a11y-003) with real descriptions and the custom-action set, and adds object-type navigation (a rotor-equivalent) so users can jump between headings, images and handwriting blocks.

#### Scope

**In:** wiring each handwriting stroke-group node's label to its on-device OCR transcript (user-editable so a mis-recognition can be corrected), each image node's label to its user/AI alt text, each shape to its recognised name + colour name; the custom-action set on every object node (delete, duplicate, change colour, bring-to-front, and **convert-to-text** for handwriting) exposed as `UIAccessibilityCustomAction`/Android custom `AccessibilityAction`/Flutter `CustomSemanticsAction`; an object-type navigation affordance (custom rotor on iOS via a platform channel, and an equivalent 'jump to next heading/image/handwriting' custom action on Android/web) per §3.1; announcing 'Converted to text' on completion.

#### Context

`docs/design/accessibility.md` §7 specifies an Immersive-Reader-class **reading mode** for typed text and OCR transcripts (never raw ink): Read Aloud with word highlight, speed and voice; a **reading-font picker including OpenDyslexic and Lexend**; adjustable size and spacing meeting WCAG 1.4.12; theme and column controls; line focus; and translation. PRD-CO-336 states it as a MUST. This is the surface that makes a handwritten notebook usable for a dyslexic or low-vision student - a wedge no ink competitor offers, and it is only possible because Sane OCRs on-device ([SN-HWR-001](ocr-hwr.md#sn-hwr-001)). [SN-DS-010](design-system.md#sn-ds-010) explicitly defers reading-mode fonts to this issue, and [SN-STDY-005](study.md#sn-stdy-005) reuses this pipeline to read flashcards aloud. The privacy trap here is real: several platform text-to-speech voices synthesise **on a server**, which would quietly ship note content off-device and break locked decision 3 and PRD-CO-000.

#### Scope

**In:** a full-screen reading surface opened from a page's overflow menu, from a transcript and from search results; single-column rendering of typed blocks plus the page's OCR transcript with the source page reference; a font picker (look body font, **OpenDyslexic**, **Lexend**) with bundled fonts + licences; size 12-48 px, line-height, paragraph, letter and word spacing controls whose ranges include and exceed the 1.4.12 minimums (1.5x / 2x / 0.12x / 0.16x); theme (look surface / sepia / high-contrast) and column-width controls; **line focus** masking 1/3/5 lines; **Read Aloud** with per-word highlight, 0.5x-2x speed, voice picker, play/pause, skip sentence and 'read from here'; persistence of all reading preferences per profile; an entry point that hands translation to Sage ([SN-AI-001](ai.md#sn-ai-001), PRD-CO-156) rather than implementing it here.

**Out:** the recognition engine and transcript production ([SN-HWR-001](ocr-hwr.md#sn-hwr-001)); typed-text editing and its own a11y ([SN-TXT-001](text.md#sn-txt-001)); translation implementation ([SN-AI-001](ai.md#sn-ai-001)); audio captions ([SN-A11Y-015](a11y.md#sn-a11y-015)); syllable splitting, parts-of-speech and picture dictionary (recorded in Technical notes as a deliberate deferral - the docs list them as Immersive-Reader parity, not a MUST).

#### Acceptance criteria

- [ ] Reading mode opens for any page that has typed text or an OCR transcript in < 500 ms on the mid-range Android reference device, and shows an honest empty state ('Nothing to read yet - convert handwriting to text first', linking convert-to-text) when neither exists.
- [ ] The font picker offers OpenDyslexic and Lexend; switching re-renders without layout break at any supported size, and spacing controls reach 1.5x line / 2x paragraph / 0.12x letter / 0.16x word with **no clipping or overlap** at 320 px width.
- [ ] Read Aloud highlights the spoken word within +/- 150 ms of the audio at 1x, 1.5x and 2x, resumes at the paused word, and stops when the surface closes or the app is backgrounded.
- [ ] **Read Aloud uses an on-device voice only**: voices that require network synthesis are filtered out of the picker; when no offline voice is installed the feature shows a clear state with a link to the OS voice settings and **never** sends text to a network TTS. Airplane-mode read-aloud works on a device with an installed offline voice.
- [ ] Raw ink is never rendered in reading mode and the source page is never modified; a correction made to the transcript here writes back through the recognition model's user-editable transcript, is undoable, and leaves the strokes untouched.
- [ ] The surface itself is accessible: every control labelled, keyboard-operable, focus visible, 44 pt / 48 dp targets, correct in all 17 looks + dark, and reduce-motion honoured ([SN-A11Y-006](a11y.md#sn-a11y-006)).

#### Technical notes

Code in `app/lib/a11y/reading_mode/`; text comes from `sane_core` typed blocks and the `sane_ml` transcript for the page ([SN-HWR-001](ocr-hwr.md#sn-hwr-001)). TTS through a thin adapter (`app/lib/a11y/reading_mode/tts_adapter.dart`) over the platform engine with an **offline-voice filter**: iOS `AVSpeechSynthesisVoice.speechVoices()` preferring downloaded enhanced/premium voices; Android `TextToSpeech` rejecting any `Voice` with `isNetworkConnectionRequired == true` or the `networkSynthesis` feature; web `SpeechSynthesisVoice.localService == true`. **Verify each API against the current SDK before implementing** (PRD-04 convention). Fonts: bundle OpenDyslexic and Lexend beside the look families from [SN-DS-009](design-system.md#sn-ds-009), with a `LICENSES.md` entry, version and provenance recorded for the SBOM. Long transcripts render with a lazy list; formatting recomputation stays off the UI isolate for large pages (CLAUDE.md §8). Implements PRD-CO-336 and `accessibility.md` §7.

#### Security & privacy

Reading aloud is a **content egress path**: a network TTS voice would transmit note text to a third party, violating locked decision 3 / PRD-CO-000. Control: the voice filter above, enforced by a negative test, plus an assertion that the adapter has no HTTP client. Transcripts and typed text are user content - never log them (CWE-532, MASVS-PRIVACY-3) and keep processing on-device (MASVS-PRIVACY-2, MASVS-NETWORK-1). A locked notebook must not be readable through this surface (PRD-LOCK-006, MASVS-PLATFORM-3, CWE-200): reading mode refuses to open for a locked notebook until it is unlocked. Bundled fonts are third-party artefacts: pin versions, record licences and include them in the SBOM (MASVS-CODE-3).

#### UX notes

Follows `accessibility.md` §7 and the design system's type scale (`design-system.md` §3) - reading mode is the **only** place OpenDyslexic/Lexend appear; look fonts stay for chrome. Entry points: page `...` menu, transcript panel, search result. Controls sit in a top bar (font, size, spacing, theme, line focus, Read Aloud) that collapses on narrow widths; all 17 looks + dark supported, with the high-contrast theme option reusing [SN-A11Y-007](a11y.md#sn-a11y-007)'s variant. Loading state while a transcript is still being produced; error state if recognition failed, with a retry.

#### Test plan

Negative: `app/test/a11y/read_aloud_voice_filter_test.dart` injects a fake TTS exposing a network-only voice and asserts it is excluded and never spoken. Golden: `app/test/golden/reading_mode_test.dart` across three looks + dark and both fonts. #### Context

Lecture audio pinned to ink is a headline Sane feature, which makes it an accessibility obligation: `docs/design/accessibility.md` §11 requires that **every recording offers time-synced captions plus a searchable transcript**, and that media controls (play/pause/stop, seek, speed) are keyboard and assistive-technology reachable. The transcription pipeline with aligned word timings already exists ([SN-AUD-020](audio.md#sn-aud-020)) and the transcript panel with export and search exists ([SN-AUD-021](audio.md#sn-aud-021)); what is missing is the **caption presentation synced to playback** and the **accessible transport**, which this issue delivers on top of the recorder bar ([SN-AUD-010](audio.md#sn-aud-010)).

#### Scope

**In:** caption segmentation as a pure function over word timings (<= 2 lines, <= 42 characters per line, >= 1 s dwell, sentence-aware splitting, gap handling); a caption view over the playback surface showing the current segment with the spoken word highlighted; a captions on/off + caption size preference persisted per profile; accessible transport - play/pause/stop labelled with state, the scrubber exposed as a semantic slider announcing `mm:ss of mm:ss` and moving in 5 s steps via arrow keys or AT increment/decrement, speed control announcing its value; the canvas audio-anchor node announcing 'audio at 04:12' with a **play** custom action feeding [SN-A11Y-004](a11y.md#sn-a11y-004)'s action set; caption export to **WebVTT and SRT** alongside the existing transcript export.

**Out:** recording and playback services ([SN-AUD-002](audio.md#sn-aud-002)); transcription and word alignment ([SN-AUD-020](audio.md#sn-aud-020)); the transcript panel, its search and its plain-text export ([SN-AUD-021](audio.md#sn-aud-021)); the recorder bar visual design ([SN-AUD-010](audio.md#sn-aud-010)); reading mode ([SN-A11Y-014](a11y.md#sn-a11y-014)); translation of captions ([SN-AI-001](ai.md#sn-ai-001)).

#### Acceptance criteria

- [ ] Every recording that has a transcript offers captions; the on/off choice and caption size persist per profile and survive restart.
- [ ] Captions track playback within +/- 150 ms at 1x, 1.5x and 2x and re-sync within 200 ms after a scrub or a skip.
- [ ] Segments never exceed 2 lines or 42 characters per line; a word longer than the line budget wraps rather than being clipped; a > 3 s silence produces no caption rather than a stale one.
- [ ] Caption text renders at >= 4.5:1 against its scrim in every look x light/dark, scales with Dynamic Type to 200% without covering the scrubber, and is never rendered directly over the waveform.
- [ ] Every transport control exposes name/role/state/value; the scrubber announces `mm:ss of mm:ss`, responds to AT increment/decrement and to arrow keys with a 5 s step, and play/pause state changes are announced.
- [ ] A recording whose transcript is not ready shows an honest state ('Transcript not ready - captions appear when it finishes'); everything works offline with no network call.
- [ ] Exported `.vtt` and `.srt` files open in a standard player with correct timings, and export happens only to a user-chosen location.

#### Technical notes

Segmentation is pure Dart in `packages/sane_audio/lib/src/captions.dart` (unit-testable, no Flutter import beyond what the package already allows); the caption view and transport semantics live in `app/lib/audio/captions/`. Consume the aligned word timings produced by [SN-AUD-020](audio.md#sn-aud-020) and the playback position stream from the audio service; do not re-run recognition. Slider semantics use `Semantics(slider: true, value:, increasedValue:, decreasedValue:, onIncrease:, onDecrease:)` so VoiceOver/TalkBack can scrub. Caption rendering uses a scrim surface from `sane_ui` rather than a per-look colour guess, so contrast holds across looks ([SN-DS-006](design-system.md#sn-ds-006) adjusted tokens where the accent is weak). Implements PRD-CO-338, PRD-LB-212/220 (audio anchors) and `accessibility.md` §3.2/§11; ADR-0015 (audio pipeline) governs the underlying pipeline.

#### Security & privacy

Transcripts and captions are **note content**: generated on-device ([SN-AUD-020](audio.md#sn-aud-020), MASVS-PRIVACY-2), never sent anywhere (MASVS-NETWORK-1), and never written to logs (CWE-532, MASVS-PRIVACY-3, CLAUDE.md §7.3). Caption export must write only to the user-selected path with canonicalised, confined paths (CWE-22, secure-coding checklist §1) and must not leak into shared caches. A locked notebook must not surface captions in previews, the lock screen or a widget (PRD-LOCK-006, MASVS-PLATFORM-3). Cached caption files derived from a recording are stored beside the encrypted blob and follow the same at-rest rules (MASVS-STORAGE-2); they are removed when the recording is deleted.

#### UX notes

Builds on the audio bar from the design (`design/Sane Notes.dc.html` Editor §7.5 - play/pause, current time, waveform + scrubber, total duration, speed 1x/1.5x/2x, 'Ink replays in sync'). Captions appear above the bar in a compact two-line block with a scrim; a CC toggle sits next to the speed control and is labelled with state. Copy follows the product voice - 'Captions - read along with what was said'. Works in all 17 looks + dark, including translucent Glass/Y2K surfaces where the scrim must be strengthened. Reduce-motion suppresses any caption slide-in ([SN-A11Y-006](a11y.md#sn-a11y-006)).

#### Context

`docs/design/accessibility.md` §2 lists the WCAG 2.2 criteria an ink app is most likely to fail, but it omits two AA criteria that are new in WCAG 2.2 and land squarely on our login flow: **3.3.8 Accessible Authentication (Minimum)** and **1.3.5 Identify Input Purpose**. 3.3.8 forbids a cognitive function test (remembering, transcribing, or re-typing a code) in any authentication step unless an alternative or a mechanism to assist exists. Our phone-OTP flow ([SN-AUTH-006](auth.md#sn-auth-006), UI in [SN-ONB-003](onboarding.md#sn-onb-003)) is exactly the pattern 3.3.8 targets: a six-digit code the user must memorise from an SMS and re-type into six separate boxes. 1.3.5 requires that fields collecting information about the user declare their purpose so autofill and symbol/icon substitution can assist. `accessibility.md` §10 only asks that the OTP input be labelled and the +91 prefix announced; it does not require paste, autofill, or password-manager support.

#### Scope

**In:** OTP entry that accepts a full paste of the code into any cell and distributes it across the boxes; platform one-time-code autofill (iOS `textContentType = .oneTimeCode`, Android SMS Retriever / `autofillHints = smsOtpCode`, web `autocomplete="one-time-code" inputmode="numeric"`); password-manager and passkey-friendly markup on every identity field (phone, email, name) via the platform autofill hints and web `autocomplete` tokens (`tel`, `email`, `name`, `given-name`); never blocking paste on any credential or code field; a visible **Resend code** path with the remaining-time announced; a documented 3.3.8 argument for each sign-in method (OIDC providers delegate the test to the IdP, which is permitted).

**Out:** the OTP transport and rate limiting ([SN-AUTH-006](auth.md#sn-auth-006)), passkey support as a feature, biometric app lock ([SN-AUTH-014](auth.md#sn-auth-014)).

#### Acceptance criteria

- [ ] Pasting a 6-digit code into the first OTP cell fills all six and submits; paste is never intercepted or stripped on any platform.

**In:** an inventory of every animation in the app with its frequency, luminance delta and area (the WCAG general/red flash thresholds care about area > 25 % of a 10-degree field and luminance change > 10 %); measurement of the worst candidates by rendering the animation offscreen and computing per-frame relative luminance in a test harness; fixes where anything approaches 3 Hz or the flash area threshold (slow it, reduce contrast delta, or make it a static state); an automated **flash-safety test** that runs the motion tokens ([SN-DS-025](design-system.md#sn-ds-025)) and a set of scripted animations through the luminance analyser and fails CI above threshold; a rule in `docs/design/ux-principles.md` and the PR checklist ([SN-A11Y-019](a11y.md#sn-a11y-019)) that new animations declare frequency and luminance delta.

**Out:** reduce-motion behaviour ([SN-A11Y-006](a11y.md#sn-a11y-006)), user-drawn content (a user animating their own ink is content, not chrome), video content ([SN-GA11-013](a11y.md#sn-ga11-013)).

#### Acceptance criteria

- [ ] An inventory table exists in `docs/design/accessibility.md` (or an appendix) listing each animation, its frequency, area and measured luminance delta.
- [ ] No app-authored animation exceeds 3 flashes per second, and none combines > 25 % screen area with > 10 % relative luminance change at any frequency above 1 Hz.
- [ ] The recording indicator, skeleton shimmer, and the Cyberpunk/Y2K accent treatments are explicitly measured and pass.
- [ ] An automated analyser test runs in CI over a set of rendered animation frame sequences and fails on a violation.
- [ ] The PR checklist requires a frequency/luminance declaration for new motion.
- [ ] Any celebration/confetti effect is capped and disabled under reduce motion.

#### Technical notes

Harness in `app/test/a11y/flash_safety_test.dart`: drive a widget with a controlled `Ticker`, capture frames via `TestWidgetsFlutterBinding` image capture, compute WCAG relative luminance per frame over the changing region, and assert transitions per second. Relative luminance code can be shared with the contrast checker from [SN-DS-007](design-system.md#sn-ds-007).

#### Security & privacy

None beyond baseline; test artefacts use synthetic fixtures. Note the safety framing in the conformance statement ([SN-A11Y-018](a11y.md#sn-a11y-018)) so the claim is evidence-backed rather than asserted.

#### UX notes

Where a pulse must slow, prefer a static state plus a text label (motion must never be the only signal, per §6). Keep the recording indicator unmistakable: steady red dot + 'Recording' label is already the reduce-motion behaviour and may simply become the default.

#### Test plan

The analyser test above; golden frame sequences for the five highest-risk animations; a manual review of any look whose accent produces high-contrast strobing; results recorded in the [SN-A11Y-017](a11y.md#sn-a11y-017) audit matrix.

#### Context

WCAG **3.3.1 Error Identification**, **3.3.3 Error Suggestion** and **3.3.4 Error Prevention (Legal, Financial, Data)** are not in the `accessibility.md` §2 matrix and no issue owns them, yet 3.3.4 applies directly to three flows we ship: **account and data deletion** ([SN-AUTH-018](auth.md#sn-auth-018)), **purchases and plan changes** ([SN-BILL-001](billing.md#sn-bill-001)), and any action that deletes user data irreversibly (empty trash, delete notebook, remove a page, revoke a share link that others depend on). 3.3.4 requires such actions to be reversible, checked, or confirmed — and the confirmation must itself be accessible: announced, keyboard-operable, with the consequence stated in text rather than implied by a red button (1.4.1). **Out:** billing checkout UI ([SN-BILL-001](billing.md#sn-bill-001)) beyond adopting this pattern, share-link revocation semantics ([SN-SHR-018](sharing-export.md#sn-shr-018)), the trash data model ([SN-LIB-001](library.md#sn-lib-001)).

#### Acceptance criteria

- [ ] Every irreversible action routes through the guard; a test enumerates destructive call sites and fails if one bypasses it.
- [ ] Confirmation dialogs state item counts and recoverability in text; the confirm button names the action; colour is never the only destructive signal.
- [ ] Focus enters the dialog, is trapped only for the modal's lifetime, returns to the invoker on cancel, and Escape always cancels.
- [ ] Deletion results are announced through the announcer ([SN-GA11-002](a11y.md#sn-ga11-002)) and, where recoverable, offer an undo action reachable by keyboard and AT within the undo window.
- [ ] Form errors are announced, programmatically associated with their field, and include a suggestion; user input is preserved.
- [ ] Account deletion requires an explicit typed confirmation and states the exact data scope and irreversibility.

#### Technical notes

Implement in `packages/sane_ui` on top of the dialog component ([SN-DS-019](design-system.md#sn-ds-019)) with a typed `DestructiveAction { titleKey, bodyKey, itemCount, recoverableFor, requiresTypedConfirmation }`. Enumerate destructive call sites with a Semgrep rule under `tools/semgrep/a11y.yml` ([SN-A11Y-019](a11y.md#sn-a11y-019)).

#### Security & privacy

Account deletion is a GDPR/DPDP right-to-erasure flow ([SN-PRV-001](privacy.md#sn-prv-001)): the confirmation must state scope accurately (local data, synced copies in the user's own drive, shared copies that cannot be recalled). Do not weaken re-authentication requirements for destructive actions to make them easier.

#### UX notes

Copy follows `docs/design/ux-principles.md` (plain language, no euphemism). Dialog layouts must survive 200% text and 320 px width ([SN-A11Y-005](a11y.md#sn-a11y-005)).

| Security controls | — |

#### Context

WCAG 2.2 AA is a locked decision (decision 10) and `docs/platform/web.md` §8 makes it a web release gate. Two of its requirements behave completely differently in a browser than on a native surface, and neither has an owner. **(1) Forced colours.** Windows High Contrast / `forced-colors: active` and browser "override page colours" modes repaint DOM content with a user's palette — but a Flutter app is a `<canvas>`, so forced-colors does *nothing* to it. A user who depends on that mode gets our normal palette, silently. [SN-A11Y-007](a11y.md#sn-a11y-007) covers OS contrast/transparency settings across all platforms, but the web media-query path, the detection, and the canvas-specific response are unaddressed (`forced-colors` appears nowhere in the backlog). **(2) Zoom and reflow.** WCAG 1.4.4 (resize text to 200%) and 1.4.10 (reflow at 320 CSS px equivalent) are browser-level behaviours, and `docs/platform/web.md` §3 flags the direct conflict: `touch-action: none` on the canvas can block user zoom. [SN-WEB-006](input-gestures.md#sn-web-006) scopes `touch-action` for palm rejection but does not own the accessibility consequence.

#### Scope

**In:** detection of `forced-colors: active` and `prefers-contrast: more` on web via a media-query bridge into Flutter; a forced-colors look that maps ink, chrome, selection and focus to the user's system colours (`Canvas`, `CanvasText`, `Highlight`, `LinkText`, `ButtonFace`) with a documented mapping table; guaranteed visible focus and selection under forced colours; full operability at **200% browser zoom** and at a 320 px reflow width without horizontal scrolling of the chrome; a verified path for user zoom on the canvas (pinch/ctrl+wheel/browser zoom) that palm rejection never blocks; and an honest capability note in Settings → Accessibility explaining what forced colours can and cannot do to handwritten ink.

**Out:** the general accessibility programme ([SN-A11Y-001](a11y.md#sn-a11y-001)), OS contrast on native ([SN-A11Y-007](a11y.md#sn-a11y-007)), canvas semantics and OCR alt-text ([SN-WEB-021](a11y.md#sn-web-021)), keyboard navigation ([SN-WEB-020](a11y.md#sn-web-020)), and the look system itself ([SN-DS-011](theming.md#sn-ds-011)).

#### Acceptance criteria

- [ ] With `forced-colors: active` (Windows High Contrast, or Chrome DevTools emulation), the app chrome renders in the user's system palette: every control, icon, border, focus ring and selection is distinguishable, and no information is conveyed by colour alone.
- [ ] Handwritten ink renders in a forced-colors-safe mapping (user text colour on user canvas colour) with a one-time inline explanation that original ink colours are preserved in the document and in exports.
- [ ] At **200% browser zoom** on a 1280×800 window, every screen is fully usable with no clipped controls and no loss of function; at a 320 CSS px reflow width the chrome stacks to one column with no horizontal page scroll (WCAG 1.4.10).
- [ ] Browser/user zoom is never blocked: with palm rejection on, pinch-zoom and ctrl+wheel still zoom **either** the page or the canvas per the documented rule, and the canvas `touch-action` scope is proven not to suppress user zoom on the rest of the page (WCAG 1.4.4).
- [ ] Text spacing overrides (1.4.12) applied through a user stylesheet or extension do not clip or overlap chrome text.
- [ ] `prefers-contrast: more` raises non-text contrast to ≥ 3:1 and text to ≥ 7:1 where the look allows, in all 17 looks and both modes.
- [ ] Automated checks run in CI: axe-core on the web chrome ([SN-A11Y-016](a11y.md#sn-a11y-016)) plus a forced-colors golden set.

#### Technical notes

Bridge the media queries with `dart:js_interop` + `matchMedia` listeners into a `WebAccessibilityPreferences` provider consumed by `SaneLookScope` ([SN-DS-011](theming.md#sn-ds-011)); do not scatter media-query reads through widgets. The forced-colors mapping is a token overlay, not a new look, so it composes with all 17 ([SN-DS-002](design-system.md#sn-ds-002)). Reflow uses the existing window size classes ([SN-DS-026](design-system.md#sn-ds-026)) — web just exercises the narrow classes at high zoom. Record the mapping table and the zoom rule in `docs/platform/web.md` §5 and `docs/design/` tokens documentation.

#### Security & privacy

No new data is processed and nothing leaves the device. Two indirect concerns: media-query state is a fingerprinting signal, so it is read for rendering only and never logged, sent or stored in telemetry (MASVS-PRIVACY-1, `PRD-PRIV-007`, CWE-532); and a forced-colors mapping must not accidentally reveal content that a look deliberately hides (for example locked-notebook placeholders must stay redacted — [SN-SEC-019](security.md#sn-sec-019), CWE-200). Accessibility settings are a special category of personal data in some regimes: they stay local (`docs/security/secure-coding-checklist.md` §11).

#### UX notes

Follows `docs/design/screens-and-flows.md` accessibility section. The ink-colour explanation appears once, inline, dismissible, and is repeated in Settings → Accessibility rather than nagging. Focus indicators keep the ≥ 3:1 requirement from [SN-WEB-020](a11y.md#sn-web-020) under forced colours by using system `Highlight`. No animation is introduced; reduce-motion continues to apply ([SN-A11Y-006](a11y.md#sn-a11y-006)).

#### Test plan

- `app/test/a11y/forced_colors_mapping_test.dart` — token overlay resolves for every look; contrast assertions.
- `app/test/a11y/reflow_zoom_test.dart` — widget tests at 200% text scale and narrow widths, no overflow.

- Manual: Windows High Contrast in Edge and Chrome, macOS Increase Contrast in Safari, recorded in the Tier 2 matrix ([SN-WEB-023](qa.md#sn-web-023)) and the accessibility audit ([SN-A11Y-017](a11y.md#sn-a11y-017)).

### SN-PHN-009

**Expose the OCR text layer to VoiceOver and TalkBack in reading mode**

| Field | Value |
|---|---|
| GitHub | not published yet |
| Type | feature |
| Priority | p1 |
| Milestone | M5 Phones & Platform Parity |
| Platforms | ios-phone, android-phone |
| Areas | a11y, ocr-hwr |
| Size | M |
| SDLC | implementation |
| Parent | [SN-PHN-001](compat.md#sn-phn-001) |
| Depends on | [SN-PHN-008](pages-canvas.md#sn-phn-008), [SN-HWR-001](ocr-hwr.md#sn-hwr-001), [SN-SRCH-002](search.md#sn-srch-002) |
| Security controls | `MASVS-PRIVACY-1`, `MASVS-PRIVACY-2`, `MASVS-PLATFORM-3` |
| Extra labels | agent-ready, innovation |

#### Context
Limitation **P6** in docs/platform/phones.md §9 is the sharpest accessibility gap in the product: handwritten notes are unreadable by screen readers, and on a phone there is no pen to re-edit them with. The mitigation the doc makes mandatory is an **OCR-backed text layer in phone reading mode** so handwritten notes are selectable, searchable and readable by TalkBack/VoiceOver (phones.md §4, §9; locked decision 10). It reuses the existing handwriting-recognition path — Vision on Apple, ML Kit on Android (docs/platform/ipad.md, docs/platform/android.md) — and on iPhone it is *the* way handwritten content becomes accessible.

This is also a market wedge: PRD-04 §8 notes that no ink app exposes handwriting to screen readers well, and Sane Notes can because it OCRs on-device (PRD-CO-310 text alternatives, PRD-CO-330 parallel accessible tree, PRD-CO-336 reading mode for transcripts — never raw ink). Recognition itself lands in M3 ([SN-HWR-001](ocr-hwr.md#sn-hwr-001)); this issue is the phone-side consumption of it.

#### Scope
**In:** the selectable OCR text layer over reading-mode pages, the parallel accessible tree (one node per stroke group / text block / image / shape) with labels and reading order, text selection and copy from recognised handwriting, the on-demand recognition trigger for pages that have no transcript yet, confidence handling and the low-confidence indication, and the honouring of the Settings 'On-device handwriting recognition' toggle.
**Out:** the recognition engine and index ([SN-HWR-001](ocr-hwr.md#sn-hwr-001), [SN-SRCH-002](search.md#sn-srch-002)), Read Aloud / reading fonts / translation (PRD-CO-336, [SN-A11Y-001](a11y.md#sn-a11y-001)), convert-to-text as an editing action (editor area), and reading mode itself ([SN-PHN-008](pages-canvas.md#sn-phn-008)).

#### Acceptance criteria
- [ ] In reading mode, every page exposes a text alternative equal to title + on-device OCR transcript; decorative strokes are marked skip-able (PRD-CO-310).
- [ ] VoiceOver and TalkBack can traverse a handwritten page in reading order and read its content; a scripted common-task run ('open notebook → read page 3 → move to page 4') passes with each screen reader (PRD-CO-331).
- [ ] The canvas publishes a parallel accessible tree with one node per stroke group, text block, image and shape, each with a label and frame (PRD-CO-330; Flutter `CustomPaint.semanticsBuilder` emitting `CustomPainterSemantics`, `ExcludeSemantics` on decorative ink).
- [ ] Transient events are announced via `SemanticsService.announce` ('Page 3 of 10', 'Transcript ready').
- [ ] Recognised text is selectable and copyable with a standard selection UI; copying respects clipboard protections for protected notebooks (PRD-LEAK-001/002).
- [ ] A page with no transcript triggers recognition **on demand, off the UI isolate**, shows a skeleton rather than a spinner, and never blocks scrolling; scrolling past a page cancels its pending recognition.
- [ ] Low-confidence regions are flagged visually and in the accessible label ('low confidence'), and raw ink remains the source of truth and is never modified (PRD-CO-154).
- [ ] With Settings → Privacy & export → 'On-device handwriting recognition' on (default), recognition runs entirely on-device and **airplane mode changes nothing**; the cloud path is unreachable.
- [ ] Recognition of a visible page completes within 1.5 s on the iPhone-ref device for a typical half-page of handwriting, and never causes a frame > 16.7 ms on the scroll path.
- [ ] The text layer is invisible to sighted users by default (it must not double-render text over the ink) but is discoverable via selection.

#### Technical notes
Consume the recognition adapter interfaces in `packages/sane_ml` (pure Dart interfaces; native impls in `plugins/sane_ml_native` — Vision/Speech on Apple, ML Kit on Android; ADR-0016) and the transcript rows already produced for the FTS index in `packages/sane_search` ([SN-SRCH-002](search.md#sn-srch-002)), so reading mode reads a cached transcript and only triggers recognition for pages that lack one. Build `app/lib/reading/a11y/` with the semantics builder and a `TextSelectionOverlay`-backed selectable layer positioned from the recognised quads. Run recognition through `Isolate.run` or the existing ML isolate — never on the UI isolate (CLAUDE.md §8). Keep transcripts in the same local store as the index (encrypted at rest with the notebook's content); do **not** create a second copy. Honour `prefs.onDevice` from Settings (docs/design/screens-and-flows.md §12). Related requirements: PRD-CO-310, PRD-CO-320, PRD-CO-330, PRD-CO-331, PRD-CO-336, PRD-LB-261 (deep-link a search hit to on-page quads).

#### Security & privacy
This issue creates a **derived copy of note content** (the transcript), which is a privacy-relevant asset, so the threat model row for stored assets must be updated. Threats and controls: **T-TRANSCRIPT-AT-REST** — a transcript stored outside the encrypted store would defeat E2EE. Control: transcripts are written through the same `sane_core` persistence and `sane_crypto` envelope as note content, never to a cache file or temp dir (MASVS-STORAGE-1, MASVS-CRYPTO-1, CWE-312). **T-CLOUD-OCR** — an adapter silently escalating to a cloud recogniser. Control: on-device by default, the cloud path is compiled behind an explicit per-request opt-in with the data-leaves-device indicator, and the Settings toggle disables it entirely; a network-capture test asserts zero note bytes leave the device (locked decision 6, PRD-CO-159, PRD-LB-222; MASVS-NETWORK-1, MASVS-PRIVACY-3, OWASP-A01). **T-A11Y-LEAK** — the accessibility tree is readable by other software on some platforms and by task-switcher snapshots; on a locked profile the tree must be suppressed along with the visual content (MASVS-PLATFORM-3, MASVS-PRIVACY-2). **T-LOG** — transcripts must never be logged (CLAUDE.md §7.3, CWE-532).

#### UX notes
Surface: phone reading mode ([SN-PHN-008](pages-canvas.md#sn-phn-008)) over the Editor canvas (docs/design/screens-and-flows.md §7.2); the privacy copy already exists and must be reused verbatim — 'On-device handwriting recognition — Your ink never leaves the device to become searchable' (§12) and 'handwriting is searched on-device' (§11). The low-confidence affordance is a subtle underline using tokens only, plus a text label, so meaning is never colour-only (PRD-CO-311). Selection handles and the copy menu come from the platform, so they inherit look-independent styling; any Sane-drawn chrome around them must pass in all 17 looks and dark mode. Loading: a per-page skeleton, never a full-screen spinner (ux-principles.md §4.2); errors are toasts with a recovery ('Could not read this page — try again'). a11y specifics: reading order follows page geometry top-to-bottom, left-to-right (mirrored under RTL, independently of left-handed mode per PRD-CO-337), targets >= 44×44 pt / 48×48 dp, and focus is never trapped.

**Audit thumb-zone reach and touch-target sizes on every phone surface**

| Field | Value |
|---|---|
| GitHub | not published yet |
| Type | design |
| Priority | p2 |
| Milestone | M5 Phones & Platform Parity |
| Platforms | ios-phone, android-phone |
| Areas | a11y, design-system |
| Size | M |
| SDLC | verification |

| Security controls | `MASVS-PRIVACY-1` |
| Extra labels | agent-ready |

#### Context
docs/platform/phones.md §7 states four one-handed rules that are easy to violate one screen at a time: primary actions (capture, save, undo, tool switch, send) live in the **bottom third**; never put a required action only in a top corner; respect iOS Reachability and Android tall-display ergonomics with sheets and dialogs sliding from the bottom; and every hover affordance inherited from tablet/desktop MUST have a tap or long-press equivalent, because phones have no hover. It also fixes the target minimum at >= 44×44 pt (iOS) / 48×48 dp (Android), which is simultaneously a WCAG 2.2 AA target-size requirement (PRD-CO-320, locked decision 10).

The design system already guarantees fixed component heights across all 17 looks — chrome buttons 42, tool buttons 44, chips 34, toggle 46×28, icon button 40×40, record button 38 (docs/design/ux-principles.md §9.2) — and two of those (chips 34, icon button 40, record 38) are **below the phone minimum**, so the phone surface needs an explicit padding/hit-area policy rather than a silent assumption. This issue is the audit that finds and fixes every violation, plus an automated check so regressions are caught in CI rather than by users.

#### Scope
**In:** an inventory of every phone surface and its interactive elements, a reach/zone classification per element, fixes for actions stranded outside the thumb zone or below the target minimum, a hit-area expansion policy for the sub-44 components, replacement of hover-only affordances with tap/long-press equivalents, and an automated target-size and top-corner-only check in the widget test suite.
**Out:** the general accessibility audit and WCAG sign-off ([SN-A11Y-001](a11y.md#sn-a11y-001), M7), the design tokens themselves ([SN-DS-002](design-system.md#sn-ds-002)), new screens, and the golden test suite ([SN-PHN-020](qa.md#sn-phn-020)).

#### Acceptance criteria
- [ ] Every phone surface from docs/design/screens-and-flows.md is inventoried: Library, Editor (toolbar, palette dock, selection bar, text-edit bar, audio bar, page rail replacement), Search, Settings, Profiles, Onboarding, Templates/Import/Share/Upgrade overlays, reading mode and the Capture hub.
- [ ] No **required** action is reachable only from the top corner of a phone screen; each has a bottom-third or sheet-based equivalent.
- [ ] Every interactive element has an effective hit area >= 44×44 pt on iOS and >= 48×48 dp on Android, even where its painted size is smaller (chips 34, icon buttons 40, record 38) — implemented as hit-area expansion, never by changing the painted size, so all 17 looks still render identically (ux-principles.md §9.2 invariant).
- [ ] Adjacent targets have >= 8 dp of separation or a combined hit area that does not overlap ambiguously.
- [ ] Every hover-only affordance from the tablet/desktop layouts has a tap or long-press equivalent on phones (phones.md §7).
- [ ] All sheets and dialogs enter from the bottom; none from the side.
- [ ] An automated widget test walks the phone widget tree of each surface and fails on any tappable element below the minimum or on a required action found only above the top 25% of the screen.
- [ ] Results hold at 200% Dynamic Type and at 320 px width with no clipping or two-dimensional scroll (PRD-CO-313, PRD-CO-314).
- [ ] Findings and fixes are recorded in a short table in `docs/design/accessibility.md` so the M7 audit can verify rather than rediscover.
- [ ] Left-handed mode mirrors reach correctly and composes with RTL independently (PRD-CO-337).

#### Technical notes
Implement the check as a reusable test helper, `app/test/a11y/target_size_matcher.dart`, that walks a pumped widget tree, resolves each `GestureDetector`/`Listener`/`Semantics(button: true)` to its hit rect, and asserts the platform minimum; drive it from a per-surface test list so adding a screen without a check is obvious. Hit-area expansion uses padding or `MaterialTapTargetSize`-equivalent wrappers inside `packages/sane_ui` components so every consumer inherits it; the painted geometry stays token-driven and unchanged (docs/design/component-inventory.md lists the affected widgets: `SaneChip`, `SaneButton(icon)`, `SaneRecordButton`, `SaneSwatch`). The reach classification is a simple three-band model (bottom third = easy, middle = reachable, top quarter = stretch) computed from the logical screen height, documented in `docs/design/accessibility.md`. No new dependency; no change to tokens.json.

#### Security & privacy
None beyond baseline — this is UI ergonomics and accessibility. Baseline that still applies: the audit tooling walks widget trees and must not dump note content, titles or user text into test output or CI logs (use structural assertions and element keys, not labels containing content) — CLAUDE.md §7.3, MASVS-PRIVACY-1, CWE-532. No new permission, no network egress, no change to stored assets, and no change to the auth or crypto paths. One adjacent security-relevant detail: destructive actions must remain confirm-gated and must not be moved into the thumb zone in a way that makes an accidental tap destructive (ux-principles.md §4.3) — the audit explicitly checks that Delete, Sign out and Purge are not adjacent to high-frequency controls.

#### UX notes
Source of truth: docs/design/screens-and-flows.md for every surface, docs/design/component-inventory.md for the widget list and their fixed heights, docs/design/ux-principles.md §9.2 for the cross-look invariants, and docs/design/accessibility.md for the contrast and target requirements. The audit must not change any painted geometry, because component heights are an invariant across all 17 looks — a chip is 34 in Brutalism and in Claymorphism alike; only the *hit area* grows. Verify in one look per family (Paper, Minimalism, Pop, Neumorphism, Brutalism) in light and dark, per the look-family guidance in ux-principles.md §9.3. Where a fix moves a control, prefer moving it into an existing bottom sheet over inventing new chrome — the page is the hero and chrome is a guest (§2).

- `app/test/a11y/phone_target_size_test.dart` — per-surface table running the matcher over Library, Editor, Search, Settings, Profiles, Onboarding, each overlay, reading mode and the Capture hub.
- `app/test/a11y/phone_reach_test.dart` — asserts no required action is only in the top quarter; destructive actions are not adjacent to high-frequency controls.
- `app/test/a11y/hover_alternative_test.dart` — every hover-revealed affordance has a tap/long-press path (negative test on a phone profile).
- `app/test/a11y/phone_text_scale_test.dart` — 200% Dynamic Type and 320 px width produce no overflow.

### SN-WEB-020

<a id="sn-web-020"></a>

**Implement keyboard-first navigation and the web shortcut map**

| Field | Value |
|---|---|
| GitHub | not published yet |
| Type | feature |
| Priority | p1 |
| Milestone | M1 Ink Editor Alpha |
| Platforms | web |
| Areas | a11y, input-gestures |
| Size | M |
| SDLC | implementation |
| Parent | [SN-WEB-001](compat.md#sn-web-001) |
| Depends on | [SN-ED-002](editor.md#sn-ed-002), [SN-WEB-002](compat.md#sn-web-002) |
| Security controls | `MASVS-PRIVACY-1`, `CWE-532` |
| Extra labels | agent-ready |

#### Context
Desktop web users expect to drive an app from the keyboard, and WCAG 2.2 AA requires it (`PRD-CO-315` = 2.1.1/2.1.2, `PRD-CO-316` = 2.4.7/2.4.11, `PRD-CO-417`). `docs/platform/web.md` §5 makes keyboard operability a **MUST** for the web app: create, search, navigate, format and undo/redo via shortcuts, visible focus rings, and skip links. Flutter paints its own UI rather than emitting DOM controls, so focus order, focus visibility and shortcut handling have to be built deliberately instead of inherited from the browser. `PRD-ED-149`–`PRD-ED-152` define the shortcut set (core editing, tool switching, bracket size/number colour, and a discoverability overlay opened with `?` on web).

#### Scope
**In:** a web shortcut map implementing `PRD-ED-149`/`PRD-ED-150`/`PRD-ED-151`, the `?` shortcut overlay (`PRD-ED-152`), focus traversal order for Library, Editor, Search, Settings and every overlay, visible focus indicators from design tokens, skip-to-content links, focus trapping and restoration in modals, and Escape-to-dismiss everywhere.
**Out:** screen-reader semantics for painted content ([SN-WEB-021](a11y.md#sn-web-021)), the shared editor state machine ([SN-ED-002](editor.md#sn-ed-002)), platform menu bars on iPadOS, and text-input/IME behaviour ([SN-WEB-030](text.md#sn-web-030)).

#### Acceptance criteria
- [ ] Every interactive control in Library, Editor, Search, Settings, Templates, Import PDF, Share and Upgrade is reachable and operable by keyboard alone, in a logical order, with **no focus trap** except intentional modal traps that restore focus on close.
- [ ] Focus is always visible with a ≥ 3:1 contrast indicator against both adjacent colours, in all **17 looks and both modes** (`PRD-CO-316`).
- [ ] Core shortcuts work: undo `Cmd/Ctrl-Z`, redo `Shift-Cmd/Ctrl-Z` and `Ctrl-Y`, copy/cut/paste, select-all, delete selection, local checkpoint `Cmd/Ctrl-S`, zoom `Cmd/Ctrl +/−/0` (`PRD-ED-149`); `Cmd/Ctrl-S` performs a **local** checkpoint and triggers no cloud action.
- [ ] Tool switches `P/H/E/L/S/T`, `Space` pan and `R` rotate work and are remappable (`PRD-ED-150`); `[`/`]` change brush size and number keys pick swatches (`PRD-ED-151`).
- [ ] No shortcut fires while a text field has focus or an IME composition is active.
- [ ] `?` opens a shortcut cheatsheet listing every binding; it is screen-reader readable and dismissible by keyboard (`PRD-ED-152`).
- [ ] A skip-to-content link is the first focusable element and works on every screen.
- [ ] Browser-reserved combinations are not hijacked, and every shortcut has a non-keyboard equivalent in the UI.

#### Technical notes
Build on Flutter's `Shortcuts`/`Actions`/`Focus` with a single declarative binding table in `app/lib/shortcuts/web_shortcut_map.dart` so bindings are testable data rather than scattered handlers; route intents into the editor state machine from [SN-ED-002](editor.md#sn-ed-002) (ADR-0003 Riverpod + go_router). Normalise `Cmd` on macOS and `Ctrl` elsewhere through a platform-aware modifier helper. Focus indicators come from `docs/design/tokens.json` via `sane_ui` ([SN-DS-002](design-system.md#sn-ds-002)) — never hardcoded colours. Remapping persists per profile (`PRD-PROF-004`). Implements `PRD-CO-417` and the keyboard row of `docs/platform/web.md` §5.

#### Security & privacy
None beyond baseline, and the baseline is not trivial here: keystrokes are note content, so **no key event, composed text or clipboard payload may ever be logged** in any build (secure-coding checklist §0.2, §7, CWE-532, MASVS-PRIVACY-1); `Cmd/Ctrl-S` must not become a network action (checklist §8 — no new egress without an ADR); pasted content is untrusted input and is sanitised before render by [SN-WEB-014](security.md#sn-web-014) (CWE-79); shortcut remappings are profile-local preferences, never synced identifiers (MASVS-PRIVACY-2).

#### UX notes
Applies across `design/Sane Notes.dc.html` screens — Sidebar (§2), Library (§6), Editor incl. toolbar, palette dock, page rail and focus mode (§7.1–§7.9), Search (§11), Settings (§12) and the overlays (§8–§10, §13). The cheatsheet is a new `sane_ui` overlay: golden-test it in two looks per mode, and verify focus-ring contrast in all **17 looks, light and dark** (a token that passes in one look can fail in another). States: cheatsheet open/closed, remap conflict warning, and a "shortcuts unavailable while typing" affordance. Accessibility: targets ≥ 44 px, contrast ≥ 4.5:1 for text and ≥ 3:1 for focus indicators, no keyboard trap, motion respects `prefers-reduced-motion` (`PRD-CO-317`).

#### Test plan
- `app/test/shortcuts/web_shortcut_map_test.dart` — binding table, modifier normalisation, suppression during text entry and IME composition.
- `app/test/web/focus_order_test.dart` — traversal order per screen and modal focus restore.
- `app/test/web/focus_ring_golden_test.dart` — focus indicator contrast in four looks across light and dark.
- `app/integration_test/web/keyboard_only_flow_test.dart` — create a notebook, write text, undo, search and export using only the keyboard.
- Manual: NVDA on Chrome/Firefox and VoiceOver on Safari for a common-task run (`PRD-CO-331`).

#### Dependencies
[SN-ED-002](editor.md#sn-ed-002), [SN-WEB-002](compat.md#sn-web-002).

### SN-WEB-021

<a id="sn-web-021"></a>

**Hand-author web canvas semantics and OCR alt-text for ink**

| Field | Value |
|---|---|
| GitHub | not published yet |
| Type | feature |
| Priority | p1 |
| Milestone | M1 Ink Editor Alpha |
| Platforms | web |
| Areas | a11y, ocr-hwr |
| Size | M |
| SDLC | implementation |
| Parent | [SN-WEB-001](compat.md#sn-web-001) |
| Depends on | [SN-ED-002](editor.md#sn-ed-002), [SN-WEB-020](a11y.md#sn-web-020) |
| Security controls | `MASVS-PRIVACY-1`, `MASVS-PRIVACY-3`, `CWE-532`, `CWE-359` |
| Extra labels | agent-ready |

#### Context
Flutter paints text and UI instead of emitting DOM controls, so its accessibility layer must be explicitly enabled and, for custom-painted content, explicitly authored — this is the single biggest known weakness of Flutter web (`docs/platform/web.md` §5 and R3, `docs/adr/0010-web-pwa-strategy.md` decision 5). The product requirement is unambiguous: the ink canvas MUST publish a **parallel accessible tree** with one node per note object / stroke group / shape / text block (`PRD-CO-330`), screen readers MUST complete all common-task flows (`PRD-CO-331`), and handwritten content MUST carry **OCR-backed text alternatives** (locked decision 10, `PRD-CO-310`). ADR-0010 warns that if the painted-text UX misses WCAG 2.2 AA, the escalation is a DOM/React web shell for web only — so this issue is also the evidence that decision rests on.

#### Scope
**In:** enabling and verifying the Flutter web semantics layer; hand-authored `Semantics` for the canvas and its object tree with roles, labels, bounds and ordering; OCR-derived alt-text attached to stroke groups where recognition output exists; semantics for the palette dock, page rail, toolbar and overlays; a screen-reader test protocol recorded in the repo; live-region announcements for state changes.
**Out:** the recognition engine that produces the text ([SN-WEB-025](ocr-hwr.md#sn-web-025), [SN-HWR-001](ocr-hwr.md#sn-hwr-001)), keyboard operation ([SN-WEB-020](a11y.md#sn-web-020)), reading mode and read-aloud (`PRD-CO-336`), and the i18n of labels ([SN-I18N-001](i18n.md#sn-i18n-001)).

#### Acceptance criteria
- [ ] The semantics tree exposes one node per note object with a meaningful role and label; an empty page announces an empty state rather than an unlabelled canvas (`PRD-CO-330`).
- [ ] NVDA on Chrome and VoiceOver on Safari can complete the common-task flow end to end: create a note, add ink, add typed text, search, and export (`PRD-CO-331`); the run is recorded as a checked-in transcript.
- [ ] Where OCR text exists for a stroke group, it is the accessible label; where it does not, the label is an honest descriptor ("handwriting, 3 lines") and never a fabricated transcription.
- [ ] Tool, page and sync state changes announce through polite live regions without interrupting writing.
- [ ] All chrome controls have labels, ≥ 44 px targets and ≥ 4.5:1 contrast in **all 17 looks, light and dark**; automated contrast checks cover every look.
- [ ] Semantics are not emitted for decorative elements; the tree stays navigable rather than noisy on a page with 500 strokes (performance measured: no frame over 16.7 ms while writing with semantics enabled).
- [ ] Turning the semantics layer on has **no measurable effect** on the B3 ink budget on Chrome desktop.

#### Technical notes
Implement as a semantics builder in `app/lib/editor/a11y/canvas_semantics.dart` fed by the document model ([SN-CORE-002](storage.md#sn-core-002)) rather than by the renderer, so nodes stay stable across repaints; batch updates so a stroke in progress does not thrash the tree. OCR alt-text is read from the recognition index when present ([SN-SRCH-002](search.md#sn-srch-002), [SN-HWR-001](ocr-hwr.md#sn-hwr-001)) and must degrade gracefully when the web has no on-device recogniser ([SN-WEB-025](ocr-hwr.md#sn-web-025)). Test with Flutter's semantics testing utilities plus real screen readers — automated checks are necessary but not sufficient (`docs/design/accessibility.md`). Record findings in `docs/platform/web.md` R3 and, if WCAG 2.2 AA cannot be met, raise the ADR-0010 escalation rather than shipping a false claim.

#### Security & privacy
Threats: an accessibility tree is a full-text mirror of note content, so it must never be logged, exported to diagnostics, or sent anywhere (TM-I-05, CWE-532, MASVS-PRIVACY-1); OCR text may contain sensitive personal data and inherits the same handling rules as note content (CWE-359, MASVS-PRIVACY-3); a locked or hidden note must not expose content through semantics while locked (`PRD-LOCK-005`/`PRD-LOCK-006` behaviour, TM-I-07). Controls: semantics are built in-memory only; no crash report or telemetry payload may include label text (ADR-0011, opt-in and redacted); locked notebooks publish a locked-state node with no content; screen-reader transcripts committed to the repo use synthetic fixture notes, never real user data.

#### UX notes
Covers the Editor canvas and chrome (`docs/design/screens-and-flows.md` §7.1–§7.9), Library (§6), Search (§11) and Settings (§12). Accessibility is the feature here: labels follow the product voice from §16, never developer jargon ("Pen, 0.6 mm, black" not "toolIdx=2"). Verify in all **17 looks and both modes** that focus, selection and state indicators are perceivable without colour alone (`PRD-CO-312`, `PRD-CO-335` colour-blind-safe palette). States: empty page, loading, recognition-unavailable, locked note, offline. Golden-test the chrome in two looks per mode; contrast-test all 17.

#### Test plan
- `app/test/web/canvas_semantics_test.dart` — tree shape, labels, ordering, locked-note behaviour, empty state.
- `app/test/web/semantics_no_pii_log_test.dart` — asserts no label text reaches `SaneLog` or a crash payload.
- `app/test/a11y/contrast_all_looks_test.dart` — programmatic contrast across all 17 looks, light and dark.
- `app/integration_test/web/screen_reader_flow_test.dart` — semantics-driven end-to-end common-task flow.
- Manual (recorded in `docs/design/accessibility.md`): NVDA + Chrome, NVDA + Firefox, VoiceOver + Safari.

#### Dependencies
[SN-ED-002](editor.md#sn-ed-002), [SN-WEB-020](a11y.md#sn-web-020); alt-text quality depends on [SN-WEB-025](ocr-hwr.md#sn-web-025).

- [ ] docs/platform/web.md R3 updated with the screen-reader result; ADR-0010 escalation raised if AA is not met
- [ ] Reviewed against docs/security/secure-coding-checklist.md §7 and §11
